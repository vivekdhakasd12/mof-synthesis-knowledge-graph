## The project in one paragraph

I am building a knowledge graph of MOF synthesis knowledge. MOFs (metal–organic frameworks) are porous materials with over 100,000 known structures, but the recipes for making them sit in plain text inside thousands of papers. I use large language models to read open-access MOF papers and pull out structured synthesis records: which metal precursor, which organic linker, which solvent, which method, at what temperature and for how long, plus measured properties and applications. Those records go into a Neo4j graph database where every fact keeps a link back to its source paper. The part that makes this a research project and not just an engineering exercise is validation: I measure, field by field, how accurate the LLM extractions are against (a) a gold standard I annotate by hand, (b) two existing databases built by older text-mining methods (DigiMOF and SynMOF), and (c) two domain baselines (ChemDataExtractor and MatSciBERT). I also compare open-weight models (Llama-3) against commercial APIs (GPT-4o, Claude) on accuracy, cost, and speed.

### 2. Re-aimed the project from broad materials to MOFs (10 June 2026)

My first draft exposé proposed benchmarking LLM extraction across all of materials science. I dropped that framing after checking the recent literature, for three reasons:

1. Bai et al. 2025 (npj Computational Materials 11:51) already built an LLM-based knowledge graph for framework materials from 100,000+ articles, including a question-answering system. The broad "can LLMs build a materials KG" question is answered.
2. My supervisor's own research is MOF graph machine learning (his MOFGalaxyNet paper, Journal of Cheminformatics 15:94). A MOF project lands in his expertise.
3. Nobody has published a rigorous per-field validation of LLM-extracted MOF synthesis data against the existing text-mined databases, and prior LLM work in this niche used only GPT models with small in-house test sets. That validation study is my gap.

The decision is recorded with full rationale in `PROGRESS.md` (entry 2026-06-10). Do not reopen it without a strong reason.

### 4. Defined the ontology (configs/ontology.json, v0.2)

Nine entity types: MOF, MetalPrecursor, OrganicLinker, Solvent, SynthesisMethod, Condition, Property, Application, Paper. Nine relation types connecting them, including a mandatory MENTIONED_IN edge from every entity to its source paper. Five open questions are listed inside the file for the first supervisor meeting (for example: should property values be nodes or attributes). The field names were chosen to line up with DigiMOF and SynMOF columns so the agreement analysis is a join, not a research project of its own.

Warning: `src/extraction/extractor_base.py` still hardcodes the old 4-entity type names from v0.1. Align those Literals (and the test) with ontology v0.2 before writing any extractor code.

- `CLAUDE.md`: standing instructions for Claude Code sessions (commands, architecture, rules). Read it once; it explains the repo faster than the README.
